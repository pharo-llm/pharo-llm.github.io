Pharo-Coder 1.0 Technical Report

Pharo-LLM team · Version 1.0

Living documentTables marked as generated are filled from the released models' data. Each release also ships a full report with that run's exact numbers in /reports.

Abstract

We present Pharo-Coder 1.0, a family of open, instruction-tuned assistants (1.5B, 3B, 7B, 14B and 32B parameters) specialised for the Pharo Smalltalk language and environment: they answer questions, write and debug code, and act as agents with tools. Starting from Qwen2.5-Coder, we continue pre-training on a deduplicated, syntax-validated corpus of permissively licensed Pharo code; restore instruction following with a chat-vector merge; and fine-tune on conversations whose every code answer was executed and verified inside a real Pharo image. We introduce PharoEval, an execution-based benchmark of 66 Pharo programming problems with a direct track and an agent track (solved through Pharo-backed tools), and gate every release on both.

1. Introduction

Smalltalk is a rounding error in the corpora of general code models. As a result they mix Pharo with Squeak and GNU Smalltalk, use the class-definition message removed in recent Pharo versions, invent selectors, and seldom produce code that installs and runs. Pharo-Coder addresses these failure modes with three ideas:

  1. Pharo-native data: the complete Pharo image plus the open-source Pharo ecosystem on GitHub, rendered in the Tonel format developers actually use.
  2. Verification by execution: every synthesized training answer is compiled and tested in a fresh Pharo image; failures are repaired using real error messages or discarded.
  3. Honest evaluation: an execution-based benchmark and a release gate.

2. Model family

All models keep the architecture and tokenizer of their base (decoder-only Transformer with grouped-query attention, RoPE, SwiGLU and RMSNorm), with a 32K-token context window.

3. Pre-training data

3.1 Sources

  • The Pharo image (MIT). A Pharo 14 image alone contains 11,533 classes and traits and 133,700 methods. After filtering and deduplication it contributes about 120K unique methods (≈12M tokens).
  • GitHub. Repositories are found by searching month by month since 2008 (to get past the API's 1,000-result cap), restricted to permissive licenses (MIT, Apache-2.0, BSD, ISC, MPL-2.0, CC0, CC-BY(-SA), EPL-2.0, …) and shallow-cloned. Tonel, FileTree and chunk-format files are parsed; README and book sources become the text part of the corpus.

3.2 Processing

  1. Line-ending normalisation (Pharo stores sources with CR line ends).
  2. Quality filters: length limits, minified or data-blob methods, generated code.
  3. Exact method-level deduplication, then syntax validation with Pharo's own parser (RBParser).
  4. Exact and near-duplicate removal at file level (MinHash, 5-token shingles, 64 permutations, LSH with 16 bands, Jaccard ≥ 0.85).
  5. Decontamination: any document sharing a 13-token n-gram with a PharoEval reference solution is removed.
  6. Each class becomes one document in Tonel format: class comment, class definition, then methods with their protocols.

4. Continued pre-training

We continue training the base checkpoint (not the instruct one) on the Pharo corpus, packed into 8,192-token sequences, with a cosine learning-rate schedule (peak 2·10⁻⁵ for 7B, lower for larger models) for two epochs. A replay slice of general code equal to 20% of the Pharo volume limits catastrophic forgetting. Training uses DeepSpeed ZeRO-3 in bf16.

5. Post-training

5.1 Chat vector

Instead of redoing the base lab's instruction tuning, we add the parameter difference between the official instruct and base checkpoints to the CPT model: θ = θCPT + α(θinstruct − θbase), with α = 1. This recovers chat ability and general instruction following, which SFT then specialises.

5.2 Execution-verified SFT data

  1. Task synthesis. A strong teacher writes exercises over 60 Pharo topics (collections, streams, exceptions, class design, patterns, SUnit, Announcements, FileSystem memory, STON, processes, …) and six task kinds (implement, extend kernel classes, bug-fix, translate, write tests, refactor). 30% are grounded in a real class from the corpus. Each task comes with 4–8 executable tests.
  2. Vetting. Tests that pass with an empty solution are removed; tasks with fewer than three remaining tests are dropped.
  3. Rejection sampling. The teacher answers each task four times, following a strict style guide (plan, complete code in canonical format, explanation, Playground example). Each answer runs in a fresh image in strict mode: all classes and methods compile; every selector sent by the new methods has an implementor in the image (rejecting hallucinated APIs that would compile but never work); all tests pass; the usage example runs without error. The most concise passing answer is kept.
  4. Repair. Failing tasks get the real Pharo errors back for up to two rounds. Successful repairs also become multi-turn "here is my error" conversations, trained on the final turn only.
  5. Grounded explanations of real methods, whose code blocks must compile.
  6. Grounded Q&A. From real class comments and documentation, the teacher writes conversations (one in three multi-turn) covering concepts, how-to, comparisons, debugging and design; plus direct answers to core Pharo topics (Metacello, Iceberg, Traits, exceptions, Announcements, SUnit, processes, …). Code in answers must compile and examples must run.
  7. Agent trajectories. The teacher works in the real tool loop (8 Pharo-backed tools). Build tasks are kept only if the agent used tools and the code it built passes the hidden tests in strict mode; exploration tasks ("where is #foo implemented and what does it do?") only if the answer names the class found in the image. The student trains on its own tool calls and answers, never on tool outputs.
  8. Real-code tasks: methods whose leading comment specifies them become "implement this method in this class" tasks; class comments become documentation tasks.

5.3 Mixture and training

Verified teacher data is upsampled 2×, explanations 1×, real-code tasks 0.5×, and 15% general code-instruction data is mixed in to preserve general ability. The student is trained with a short system prompt (not the teacher's style guide), so it internalises the style. Loss is computed on assistant tokens only, including the end-of-turn token; over-long samples are dropped, never truncated.

6. Evaluation

6.1 PharoEval

66 problems across 14 categories, each with executable tests. A problem is solved only if the answer installs in a fresh image and all tests pass. References are verified to pass and empty answers to fail. See PharoEval.

6.3 Agent track

PharoEval-Agent solves the same problems through the tool loop and scores the code built in the session. Results appear in the Agent column of the table above.

6.4 Release gate

A model is exported and published only if (a) its PharoEval pass@1 exceeds a size-specific minimum and (b) it beats its own base instruct model by at least 5 points, and (c) its agent score is not below the base model's. Tool calling of the Ollama build is re-checked on the agent track. The default quantized GGUF is then re-evaluated through Ollama, testing the exact artifact users download, and the release is blocked if it loses more than 5 points.

7. Limitations

  • PharoEval measures self-contained tasks, not GUI work (Spec), visualisation (Roassal), web (Seaside) or large-codebase navigation.
  • Selector checks catch invented messages, but not every wrong use of real ones. Run the code and its tests.
  • The models target Pharo 12 and later (fluid class definitions); older images need the legacy syntax.

8. Conclusion

Verification by execution turns a small language's scarce data into reliable supervision. Because the entire pipeline is automated, from mining to publication, Pharo-Coder can be refreshed as the ecosystem evolves, and each snapshot is measured the same way.
