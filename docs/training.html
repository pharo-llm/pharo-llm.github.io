Training pipeline

Every Pharo-Coder release is produced by one automated, resumable pipeline: pharo-one.

pharo-one run --config configs/pharo-coder-1.0-mini.yaml

Stages

#StageWhat it does
1setupDownloads a clean Pharo image + VM and validates PharoEval itself.
2mineDumps every class of the (MIT) Pharo image; searches GitHub month by month, keeps permissive licenses, shallow-clones, parses Tonel, FileTree and chunk files.
3corpusQuality filters, exact + MinHash dedup, real-parser syntax validation, decontamination; renders each class as a Tonel file.
4sft_dataTasks from real code + teacher-synthesized exercises with tests, rejection-sampled and verified in Pharo, repair rounds, mixing.
5cptContinued pre-training of the base model on the Pharo corpus (+ general-code replay).
6chat_vectorAdds (Instruct − Base) to restore instruction following.
7sftSupervised fine-tuning, loss on assistant turns only.
8evalPharoEval for the new model, the base instruct model, ablations and previous releases.
9gateStops the release unless it beats the base model by a configured margin.
10exportGGUF conversion and quantization, Ollama models, and re-evaluation of the GGUF through Ollama.
11publishModel cards, Hugging Face uploads (safetensors, base, GGUF), Ollama push.
12site, reportUpdates this website's model catalog and generates the technical report from the run's real numbers.

Verified SFT data

A teacher answers each synthesized exercise several times. An answer is kept only if, in a fresh image, all classes and methods compile, every sent selector has at least one implementor in the image (catching invented APIs), all tests pass, and the usage examples run. Failing answers get the real Pharo errors back for repair; successful repairs also become multi-turn debugging conversations.
